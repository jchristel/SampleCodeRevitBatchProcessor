# Database Design - Document Revision Management

## Overview

This database design supports a document revision management system where documents are tracked through multiple revisions and organised into release batches. Each project maintains its own file-based database to allow for project-specific customisation.

## Core Requirements

### Document Requirements
Each document must have these minimum fields:
- **Number**: Alphanumeric document identifier (can contain numbers and characters)
- **Name**: Full document name (can contain numbers and characters)
- **Revision**: Revision indicator (can be number, character, or both - e.g., "1", "A", "2B")
- **Revision Date**: Date when the document was issued

### Revision Requirements
Each revision batch must have these minimum fields:
- **Revision Date**: When documents in this batch were issued
- **Description**: Optional context (e.g., "For Construction", "For Tender")

## Key Business Rules

### Document Versioning
- The same document (identified by Number) can have multiple entries in the database
- Each entry represents a different revision of that document over time
- Revision indicators are extracted from the document name (not auto-generated by the system)

### Revision Batches
- One revision date can have many documents issued under it
- Documents issued on the same date can have completely different revision indicators
- Example: On the same revision date, Document A might be at revision "1" while Document B is at revision "3"

### Multiple Revisions Per Day
- Multiple revision batches can occur on the same day for different reasons
- Each batch gets a unique identifier to distinguish between same-day releases
- Example: Morning release "For Construction" and afternoon release "For Permit Submission"

## Database Schema

### Revisions Table
Represents release batches or issuance events.

**Primary Key**: Auto-increment integer ID
**Purpose**: Groups documents that were issued together

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| Id | INT (Identity) | Yes | Unique identifier for each revision batch |
| RevisionDate | DATETIME | Yes | Date when documents were issued |
| Description | NVARCHAR(255) | No | Context for this revision (e.g., "For Construction") |

### Documents Table
Stores individual document versions with complete revision history.

**Primary Key**: Auto-increment integer ID
**Purpose**: Tracks every version of every document

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| Id | INT (Identity) | Yes | Unique identifier for each document version |
| Number | NVARCHAR(50) | Yes | Document identifier |
| Name | NVARCHAR(255) | Yes | Full document name |
| Revision | NVARCHAR(10) | Yes | Revision indicator (parsed from document) |
| RevisionId | INT | Yes | Foreign key to Revisions table |

### Relationship Structure
- **One-to-Many**: Revisions → Documents
- **Foreign Key**: Documents.RevisionId → Revisions.Id
- **Indexing**: Performance indexes on Number, RevisionId, and composite Number+Revision

## Customisation Support

### Project-Specific Fields
Each project database can extend the Documents table with additional fields:

**Common Extensions:**
- ProjectPhase (NVARCHAR) - e.g., "Design", "Construction"
- DisciplineCode (NVARCHAR) - e.g., "ARCH", "MECH", "ELEC"
- FilePath (NVARCHAR) - Location of physical document file
- Status (NVARCHAR) - e.g., "Active", "Superseded", "Archived"
- Author (NVARCHAR) - Document creator
- Reviewer (NVARCHAR) - Document reviewer
- DrawingSize (NVARCHAR) - e.g., "A1", "A3"
- DrawingType (NVARCHAR) - e.g., "Plan", "Section", "Detail"

### File-Based Database Benefits
- **Portability**: Each project database is self-contained
- **Customisation**: Schema can be modified per project needs
- **Isolation**: Projects don't interfere with each other
- **Backup**: Simple file-level backup and restore
- **Deployment**: Easy to distribute project databases

## Data Flow Examples

### Example 1: Same Date, Different Revisions
**Revision Batch**: March 15, 2024 - "For Construction"
- Document "A-101" Floor Plan → Revision "3"
- Document "S-201" Structural → Revision "1"
- Document "M-301" Mechanical → Revision "2"

### Example 2: Multiple Batches Same Day
**Morning Batch**: March 15, 2024 - "For Construction"
- Document "A-101" → Revision "3"

**Afternoon Batch**: March 15, 2024 - "For Permit Submission"
- Document "A-102" → Revision "1"
- Document "A-101" → Revision "4" (updated version)

### Example 3: Document History
Document "A-101" revision history:
1. January 10, 2024 - Revision "1" - "Initial Design"
2. February 5, 2024 - Revision "2" - "Design Development"
3. March 15, 2024 - Revision "3" - "For Construction"
4. March 15, 2024 - Revision "4" - "For Permit Submission"

## SQLite Implementation Strategy

### NuGet Package Usage

**sqlite-net-pcl**: Primary ORM for all database operations
- Entity mapping with attributes
- Simple CRUD operations
- Type-safe queries with LINQ
- Automatic table creation from C# classes
- Raw SQL execution via `ExecuteAsync` / `ExecuteScalarAsync` for advanced operations such as PRAGMAs, custom indexes, and integrity checks

No separate low-level SQLite package is required. All advanced SQL needs are covered by the `ExecuteAsync` / `ExecuteScalarAsync` methods on the sqlite-net-pcl connection.

### Database File Management
- **File Location**: Each project maintains its own `.sqlite` database file
- **Naming Convention**: `{ProjectName}_{ProjectId}.sqlite`
- **Portability**: Database files can be copied/shared between systems
- **Backup Strategy**: Simple file-level backup and restore

### Connection Management
- **Foreign Key Support**: Must be explicitly enabled in SQLite connection
- **WAL Mode**: Not used. WAL mode is unreliable on network shares (SMB/CIFS), which is the primary deployment target for this application. The busy timeout approach is the correct concurrency mitigation for this usage pattern.
- **Busy Timeout**: Both the async and sync connections are configured with a 5-second busy timeout immediately after creation. SQLite will wait and retry before throwing `SQLiteBusyException`, which eliminates nearly all collision errors for the expected 2–3 concurrent user pattern.
- **Connection Instances**: One async connection (`SQLiteAsyncConnection`) and one sync connection (`SQLiteConnection`) per database, managed by `DatabaseService`. The sync connection exists solely to support IronPython/PyRevit via the Revit plugin.
- **Transaction Management**: All multi-step write operations must be wrapped in a transaction. Use `IUnitOfWork.RunInTransactionAsync` (async path) or `IUnitOfWorkSync.RunInTransaction` (sync path). Single-row operations do not require explicit transactions.

### Concurrency and External Change Detection
DocManager operates with two concurrent clients writing to the same database file:
- **DocManager Standalone** — WPF desktop application (async path)
- **DocManager for Revit** — Revit plugin using IronPython (sync path)

The expected concurrent usage profile is 2–3 users with infrequent simultaneous writes. SQLite is appropriate for this pattern. The busy timeout is the primary hardening measure.

When the standalone app is open and a Revit user adds documents, the standalone app detects this via SQLite's built-in `PRAGMA data_version`. This pragma returns an integer that increments whenever any connection writes to the database. The standalone app polls this value on a 30–60 second interval using a `PeriodicTimer`. If the value has increased since the last check, the affected data is reloaded. The Revit plugin does not poll — it is the writer.

`IDatabaseService` exposes `GetDataVersionAsync()` (async path) and `GetDataVersion()` (sync path) for this purpose.

## Future Extensions

### Potential Enhancements
- Document relationship tracking (references, dependencies)
- Digital signature/approval workflow integration
- File attachment management
- Change tracking and comparison
- Automated revision numbering rules
- Integration with document management systems

### Future Upgrade Path
If the concurrent user count grows significantly beyond 2–3, or if network share file locking issues are observed in practice, the recommended upgrade paths are:

- **Lightweight service layer**: Run a small REST or gRPC service on the machine hosting the database. All clients communicate with the service rather than directly with the file. `IDatabaseService` is the correct seam for this change — repository and ViewModel code remains untouched.
- **SQL Server Express**: Free, integrates naturally into Windows environments, and supports true concurrent writes. The repository pattern already isolates all database access, so migration is bounded to the repository and `DatabaseService` classes only.
